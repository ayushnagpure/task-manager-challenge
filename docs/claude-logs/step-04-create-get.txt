     Task Manager — Implementation Plan (rev 2)

     Context

     The repo is empty except for CLAUDE.md, .gitignore and docs/claude-logs.
     We're building a small task manager:
     a .NET 9 Web API (EF Core Code First, SQL Server Express
     localhost\SQLEXPRESS, DB TaskManagerDb)
     with a React + Vite UI. Features: list (filter by status/priority), get by
     id, create, update, soft delete,
     and GET /api/tasks/summary using raw SQL (not EF) for counts grouped by
     status and priority.
     Environment: .NET SDK 9.0.307 installed (plus 6/7/8), Node 26 / npm 11.

     Decisions

     - Test DB: SQLEXPRESS TaskManagerDb_Tests + Respawn (ignores
       __EFMigrationsHistory)
     - Raw SQL: plain ADO.NET (Microsoft.Data.SqlClient)
     - Summary: flat list, only combinations that have tasks
     - Seeding: HasData in migration, ~15 tasks
     - Priority: Low, Medium, High, Critical. Entity has AssignedTo. Timestamps
       are CreatedDate / ModifiedDate
     - global.json: 9.0.100 with rollForward: latestFeature (stays on 9.0.x and
       never moves to 10)
     - Steps 1 and 2 merged into one iteration
     - Defaults (change any you like): int identity ids; DataAnnotations; no
       list pagination; no auth;
       built-in logging; UI calls API via VITE_API_BASE_URL + CORS; plain xUnit
       Assert

     1. Solution layout

     TaskManager.sln, global.json, Directory.Build.props, 
     Directory.Packages.props (central, Microsoft.* 9.0.x)
     src/TaskManager.Api/   Controllers/ Contracts/ Domain/ Data/ Services/ 
     Infrastructure/ Program.cs
     tests/TaskManager.Tests/  Unit/  Integration/
     src/task-manager-ui/   src/api/ src/components/ src/hooks/
     No shared library: the API and its tests are the only C# consumers, and the
     UI is JS. Entity is TaskItem
     so it doesn't clash with System.Threading.Tasks.Task. The table is Tasks
     and the route is /api/tasks.

     2. Entity & soft delete

     TaskItem: Id int; Title required, max 200; Description max 2000 (nullable);
     Status (Todo,
     InProgress, Done); Priority (Low, Medium, High, Critical); AssignedTo
     (nullable, max 100);
     DueDate (DateOnly?); CreatedDate / ModifiedDate (DateTimeOffset, UTC, from
     injected
     TimeProvider); IsDeleted; DeletedDate (DateTimeOffset?); RowVersion
     (rowversion).
     - Enums stored as strings (HasConversion<string>(), max 20). The API uses
       JsonStringEnumConverter.
     - Global filter !IsDeleted. Index on (IsDeleted, Status, Priority).
     - Soft delete happens explicitly in the service. Deleting a missing or
       already-deleted task returns 404.

     Sorting caveat: because enums are stored as strings, a plain ORDER BY 
     Priority sorts alphabetically
     (Critical, High, Low, Medium). Both the LINQ and the SQL sort map priority
     to a rank with a CASE:
     - LINQ (list): query.Where(status?).Where(priority?)
       .OrderByDescending(t => t.Priority == Critical ? 4 : t.Priority == High ?
       3 : t.Priority == Medium ? 2 : 1)
       .ThenByDescending(t => t.CreatedDate). EF translates this to SQL CASE. A
       test checks the order.
     - Summary SQL:
     SELECT Status, Priority, COUNT(*) AS [Count]
     FROM dbo.Tasks
     WHERE IsDeleted = 0
     GROUP BY Status, Priority
     ORDER BY CASE Status WHEN 'Todo' THEN 1 WHEN 'InProgress' THEN 2 WHEN
     'Done' THEN 3 END,
              CASE Priority WHEN 'Critical' THEN 1 WHEN 'High' THEN 2 WHEN
     'Medium' THEN 3 WHEN 'Low' THEN 4 END;
       The SQL is a constant string. Any future filters will go only through
     typed SqlParameters.

     3. Update: PUT vs PATCH (decide before step 7)

     My recommendation is to keep PUT for the edit form and also add PATCH 
     /api/tasks/{id}/status
     with body { "status": "Done" }. It returns the updated TaskResponse,
     including the new rowVersion.
     - A dropdown that has to send title, description, assignee etc. back just
       to change status is wasteful.
       It also risks overwriting another user's edits with stale values. That
       second problem is worse than a 409.
     - A single-field, purpose-built endpoint is easy to validate with
       DataAnnotations. I'm not using JSON Patch
       (RFC 6902): it needs Newtonsoft and generic operations are hard to
       validate.
     - The status PATCH doesn't require a rowVersion: last write wins for that
       one field, which is the sensible
       behaviour for a status toggle. PUT keeps rowVersion → 409, because it
       replaces every field.
     - The UI must replace its cached task (rowVersion included) with the PATCH
       response so a later PUT doesn't 409.
       If you prefer one endpoint only, the alternative is keeping PUT and
       having the dropdown send the full task.

     4. Validation & errors (one shape: RFC 7807 ProblemDetails + traceId)

     - [ApiController] + DataAnnotations → 400 ValidationProblemDetails. Bad
       enum, JSON or query values also end up here.
     - GlobalExceptionHandler : IExceptionHandler + AddProblemDetails():
       NotFoundException→404,
       DbUpdateConcurrencyException→409, BadHttpRequestException→400, everything
       else→500 with a generic message.
       No stack trace and no exception message is sent to the client.
     - UseStatusCodePages() so unknown routes and 405s also return
       ProblemDetails. CustomizeProblemDetails adds traceId.

     5. Logging

     Built-in ILogger. Exceptions are logged in the handler with the traceId
     (Error for 5xx, Warning for 4xx).
     UseHttpLogging records method, path, status and duration only (no bodies).
     Services log structured events
     ({TaskId}, {Priority}). Connection strings and bodies are never logged.

     6. Seeding (HasData)

     Data/SeedData.cs: 15 tasks with fixed Ids 1–15 and literal dates, so new
     migrations don't keep
     re-emitting the seed rows. 12 are active and cover all 12 status × priority

  Things you should know

  - Disallowed request headers: ASP.NET Core still sends
    Access-Control-Allow-Origin when a preflight asks for a header we don't
    allow, such as Authorization. It just leaves that header out of
    Access-Control-Allow-Headers, and the browser blocks the request. My first
    test expected no origin header at all and failed, so I changed it to check
    this actual behaviour.

     Decisions (all four confirmed by you)

     1. Bad input → 400 ValidationProblemDetails, keyed by field name.
        - Status and Priority are string in the request DTO, validated by a
          custom [EnumName(typeof(TaskPriority))]
          attribute. The error looks like errors.Priority: ["Priority must be 
          one of: Low, Medium, High, Critical."].
        - The comparison ignores case; the service parses the value. Numeric
          enum values are rejected.
        - Why not typed enums in the request: with typed enums, System.Text.Json
          fails during deserialization. The
          error key then becomes $.priority, the message leaks
          TaskManager.Api.Domain.TaskPriority, and
          JsonStringEnumConverter accepts integers by default, so "priority": 99
          would get through.
        - Title: [Required] (rejects null, "" and whitespace) and
          [StringLength(TaskItemConfiguration.TitleMaxLength)].
          Description and AssignedTo use [StringLength] with their constants.
        - Malformed JSON: AllowInputFormatterExceptionMessages = false gives a
          generic "The input was not valid."
          under a $... key, with no parser or type details.
          SuppressImplicitRequiredAttributeForNonNullableReferenceTypes = true
          stops the noisy extra "request field is required" error; every
          required field gets an explicit [Required].
        - Response enums still serialize as strings. I'll also set
          JsonStringEnumConverter(allowIntegerValues: false).
     2. Create → 201 Created + Location: /api/tasks/{id} + the full TaskResponse
        body, the same shape GET returns.
        The UI gets server values (id, dates, rowVersion) without a second call.
        This uses CreatedAtAction(nameof(GetById), …).
     3. rowVersion is in TaskResponse as a base64 string (System.Text.Json's
        default for byte[]). Step 6's PUT
        sends it back. The ETag/If-Match alternative would be more HTTP-correct,
        but it needs CORS
        WithExposedHeaders("ETag") and header plumbing in the UI. A body field
        is simpler.
     4. Soft-deleted id → 404, identical to an unknown id, so a deleted task's
        existence isn't revealed. The global
        filter hides the row, the service throws NotFoundException, and the
        existing handler returns 404 ProblemDetails.
        id = 0 (or "abc") → 404, because the route constraint {id:int:min(1)}
        doesn't match. It goes through status code pages, so it's still
        ProblemDetails.

  src/TaskManager.Api/Validation/EnumNameAttribute.cs

  using System.ComponentModel.DataAnnotations;

  namespace TaskManager.Api.Validation;

  /// <summary>
  /// Validates that a string is the name of a member of <see cref="EnumType"/> 
  (case-insensitive).
  /// Numbers, comma-separated flag combinations and unknown names are rejected.
  Null is treated as
  /// valid; combine with <see cref="RequiredAttribute"/> when a value is 
  mandatory.
  /// </summary>
  [AttributeUsage(AttributeTargets.Property | AttributeTargets.Parameter | 
  AttributeTargets.Field)]
  public sealed class EnumNameAttribute : ValidationAttribute
  {
      public EnumNameAttribute(Type enumType)
      {
          ArgumentNullException.ThrowIfNull(enumType);
          if (!enumType.IsEnum)
          {
              throw new ArgumentException($"{enumType.Name} is not an enum
  type.", nameof(enumType));
          }

          EnumType = enumType;
      }

      public Type EnumType { get; }

      public override bool IsValid(object? value) =>
          value is null || (value is string text && FindName(EnumType, text) is
  not null);

      public override string FormatErrorMessage(string name) =>
          $"{name} must be one of: {string.Join(", ", 
  Enum.GetNames(EnumType))}.";

      /// Parses a value that has already passed validation. Throws if the value
  is not a member name.
      public static TEnum Parse<TEnum>(string value)
          where TEnum : struct, Enum =>
          FindName(typeof(TEnum), value) is { } name
              ? Enum.Parse<TEnum>(name)
              : throw new ArgumentException($"'{value}' is not a valid
  {typeof(TEnum).Name}.", nameof(value));

      private static string? FindName(Type enumType, string value) =>
          Enum.GetNames(enumType).FirstOrDefault(name => string.Equals(name,
  value, StringComparison.OrdinalIgnoreCase));
  }
  (The real file also has XML doc comments; I've left them out here.)

  Why it compares against the enum's names instead of calling Enum.TryParse:
  Enum.TryParse accepts "2", and it also accepts "Low, High". That second one
  combines into the value 2, which is High, so both strings would get through.
  Comparing against the declared names only lets real names in.

  It doesn't trim either, so " Low" is rejected.

  using Microsoft.EntityFrameworkCore;

  namespace TaskManager.Api.Services;

  /// <summary>EF Core implementation of <see cref="ITaskService"/>.</summary>
  public sealed class TaskService : ITaskService
  {
      private const string ResourceName = "Task";

      private readonly TaskDbContext _db;
      private readonly TimeProvider _timeProvider;
      private readonly ILogger<TaskService> _logger;

      public TaskService(TaskDbContext db, TimeProvider timeProvider,
  ILogger<TaskService> logger)
      {
          _db = db;
          _timeProvider = timeProvider;
          _logger = logger;
      }

      public async Task<TaskResponse> CreateAsync(CreateTaskRequest request,
  CancellationToken cancellationToken)
      {
          ArgumentNullException.ThrowIfNull(request);

          var now = _timeProvider.GetUtcNow();
          var task = new TaskItem
          {
              Title = request.Title!.Trim(),
              Description = NullIfBlank(request.Description),
              Status = request.Status is null ? TaskItemStatus.Todo :
  EnumNameAttribute.Parse<TaskItemStatus>(request.Status),
              Priority =
  EnumNameAttribute.Parse<TaskPriority>(request.Priority!),
              AssignedTo = NullIfBlank(request.AssignedTo),
              CreatedDate = now,
              ModifiedDate = now,
          };

          _db.Tasks.Add(task);
          await _db.SaveChangesAsync(cancellationToken);

          _logger.LogInformation("Created task {TaskId} with status {Status} and
  priority {Priority}", task.Id, task.Status, task.Priority);
          return task.ToResponse();
      }

      public async Task<TaskResponse> GetByIdAsync(int id, CancellationToken 
  cancellationToken)
      {
          var task = await _db.Tasks.AsNoTracking().FirstOrDefaultAsync(t =>
  t.Id == id, cancellationToken)
              ?? throw new NotFoundException(ResourceName, id);

          return task.ToResponse();
      }

      private static string? NullIfBlank(string? value) =>
          string.IsNullOrWhiteSpace(value) ? null : value.Trim();
  }
  Things to look at:
  - Time is read once. GetUtcNow() is called once, so CreatedDate and
